{{ if .Values.gateway.enabled -}}
GATEWAY ENABLED — public path through EKS, no NodePort anywhere:
  internet -> ALB (ip targets) -> gateway pod -> {{ .Values.vllm.serviceName }} -> Liqo -> OVH pod

  kubectl -n {{ .Values.gateway.namespace }} get ingress vllm-gateway -w

An empty ADDRESS with no events means aws-load-balancer-controller is missing:
  make alb-controller

Once ADDRESS appears:
  ADDR=$(kubectl -n {{ .Values.gateway.namespace }} get ingress vllm-gateway \
    -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
  curl http://$ADDR/healthz     # the gateway itself; 200 as soon as targets register
  curl http://$ADDR/v1/models   # the model, through Liqo

Reading the two apart is the point of /healthz:
  200 on /healthz, 502 on /v1/models -> AWS side fine, no GPU machine or vLLM
                                        still loading
  503 on /healthz                    -> no healthy targets: the ALB cannot reach
                                        the gateway pods. Check the controller
                                        log, not the model.
{{- else }}
Reach it through EKS with no AWS resources at all:
  kubectl -n {{ .Values.namespace.name }} port-forward svc/{{ .Values.vllm.serviceName }} {{ .Values.vllm.port }}:{{ .Values.vllm.port }}
For a public address, set gateway.enabled=true (ALB, needs
`make alb-controller`) or vllm.service.type=LoadBalancer (NLB, nothing extra to
install).
{{- end }}

{{- if .Values.cpu.heartbeat.enabled }}

Heartbeat — one line every {{ .Values.cpu.heartbeat.intervalSeconds }}s, naming the machine that ran it:
  kubectl -n {{ .Values.namespace.name }} logs -f deploy/{{ .Values.cpu.name }} -c heartbeat

That stream is served by Liqo's virtual kubelet proxying to the remote K3s API,
so a ticking clock proves the CONTROL-PLANE path back from the rented machine —
which can be broken while the pod still reads Running.

peering failure — compare its request against the node:
  kubectl describe node -l external-node-autoscaler/pool | grep -A5 Allocatable
